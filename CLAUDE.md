# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Semantic Logger is a Ruby gem: a feature-rich, multi-destination logging framework and replacement for Ruby & Rails loggers. Its defining trait is **asynchronous logging** — log events are pushed onto an in-memory queue serviced by a background thread, so the application is not blocked while logs are written to one or more destinations ("appenders").

Rails users should use the sister gem `rails_semantic_logger`, not this gem directly.

**Sister gem version lockstep:** `rails_semantic_logger` is locked to the same major version of this gem. As of v5 it has been upgraded in lockstep: it is on v5.3 and its gemspec requires `semantic_logger ">= 5.3"`, with no upper bound, so its 5.x releases would also accept v6. Major-version changes here must continue to be mirrored there. The v5 internal refactors (the `QueueProcessor` extraction and the removal of `Appender::AsyncBatch`) have been accounted for; the sister gem does not reference `AsyncBatch` directly. The sister gem lives at `/Users/reidmo/src/rails_semantic_logger` (when checked out locally).

## Public interface

The **only** public-facing interface is the `SemanticLogger` module itself ([lib/semantic_logger/semantic_logger.rb](lib/semantic_logger/semantic_logger.rb)): its module methods (`SemanticLogger[...]`, `add_appender`, `default_level=`, `tagged`, `silence`, `flush`, `reopen`, etc.) plus the `Loggable` mixin. Everything else (`Logger`, `Base`, `Processor`, `Subscriber`, `Appender::*`, `Formatters::*`, `Log`, ...) is **internal** and may be refactored freely, as long as the public interface keeps working.

The one wrinkle: once a `Logger` instance has been handed back (via `SemanticLogger['ClassName']` or the `logger` method from `Loggable`), that instance's API (`info`, `measure_info`, `tagged`, `level=`, ...) is also part of the public contract. But end users never need to know *how* a `Logger` is constructed — it is always obtained through the `SemanticLogger` module or the `Loggable` mixin, so the constructor and the class itself remain internal.

When changing internal classes, the bar is: **do not break any existing public-facing interface** (the `SemanticLogger` module methods or a returned `Logger`'s methods).

The Ruby `Logger` compatibility aliases in [lib/semantic_logger/concerns/compatibility.rb](lib/semantic_logger/concerns/compatibility.rb) (`<<`, `add`, `progname`, `sev_threshold`, `silence_logger`, ...) are **not** part of the published public interface. They exist solely so Semantic Logger can stand in for the Ruby/Rails loggers (Rails and libraries like Active Record's session store call them), so they must keep working for that purpose, but do not document, extend, or promote them as public API.

## Commands

```bash
LOGGER_SYNC=1 bundle exec rake   # run tests in synchronous mode (no background thread)
```

Run a single test file or test:

```bash
bundle exec ruby -Itest test/logger_test.rb
bundle exec ruby -Itest test/logger_test.rb -n /pattern/
```

Some appender tests need MongoDB. CI runs against Ruby 3.2–4.0 with a MongoDB service on `127.0.0.1:27017` (`MONGO_HOST` env var). Use `docker compose up` (see `docker-compose.yaml`) to start a local MongoDB container; the tests themselves run on the host.

The minimum supported Ruby is 3.2 (as of v5; see `gemspec` and `.rubocop.yml`'s `TargetRubyVersion`) — do not use syntax newer than that in `lib/`.

## Architecture

The logging pipeline has four layers. Understanding the hand-off between them is the key to this codebase:

1. **`SemanticLogger::Logger`** ([lib/semantic_logger/logger.rb](lib/semantic_logger/logger.rb)) — what application code holds (one per class, via `SemanticLogger['ClassName']` or the `Loggable` mixin). `logger.info(...)` etc. build a `Log` object and hand it to the global processor. There is **one shared processor** for the whole process (`Logger.processor`), not one per logger.

2. **`SemanticLogger::Base`** ([lib/semantic_logger/base.rb](lib/semantic_logger/base.rb)) — abstract superclass of both `Logger` and `Subscriber`. It metaprograms the per-level methods (`debug`/`info`/`warn`/..., plus `measure_*`) from `Levels::LEVELS`, and contains the argument-parsing logic in `log_internal` / `measure_internal` that turns the flexible call signatures (message, payload hash, exception, block) into a populated `Log`.

3. **`SemanticLogger::Processor`** ([lib/semantic_logger/processor.rb](lib/semantic_logger/processor.rb)) — a singleton that **is** an `Appender::Async`. It owns the background thread and the queue. It fans each `Log` out to the `Appenders` collection. `SyncProcessor` ([lib/semantic_logger/sync_processor.rb](lib/semantic_logger/sync_processor.rb)) is the drop-in replacement used when `SemanticLogger.sync!` is called (or `require "semantic_logger/sync"`), which logs inline on the calling thread — used heavily in tests.

4. **`SemanticLogger::Subscriber`** ([lib/semantic_logger/subscriber.rb](lib/semantic_logger/subscriber.rb)) — the abstract base class for **all appenders** (despite the name). Each appender writes a `Log` to one destination, using its own `Formatter`. Concrete appenders live in [lib/semantic_logger/appender/](lib/semantic_logger/appender/).

### Sync vs. Async layering

`Appender::Async` ([lib/semantic_logger/appender/async.rb](lib/semantic_logger/appender/async.rb)) is a **proxy** that wraps a real appender and runs it in a separate thread with a queue, in either streaming or batched mode. `Appender.factory` ([lib/semantic_logger/appender.rb](lib/semantic_logger/appender.rb)) decides at construction time whether to wrap an appender in `Async` and whether to enable batching (batch is automatic if the appender implements `#batch` and opts in via `#batch_by_default?`, or explicit via `batch: true`). Before batching, it asks the appender's `#batch_refusal`, which returns nil or why the appender cannot be batched and what to do instead, and raises `ArgumentError` with it. `Subscriber` answers nil, since a `#batch` that uses `format_log` works with any formatter; a class whose own `#batch` formats the whole batch with `format_batch` (`Appender::Http`, `Loki`) refuses a formatter without `#batch(logs, logger)`, through the private `Subscriber#format_batch_refusal` that `format_batch` raises with too, but only while its own `#batch` is the one in use (the private `Subscriber#batch_defined_by?`, which finds the method's owner with `Kernel#method`, since an appender may define its own `#method`), so that a subclass that replaces `#batch` is not refused. A subclass whose `#batch` calls `super` is not refused either, so it must define `#batch_refusal` itself, returning `format_batch_refusal`. `Appender::ElasticsearchHttp` overrides `#batch_refusal` to refuse whatever the formatter while `Http#batch` is in use, since Elasticsearch takes a batch only through its bulk API. `build` returns the appender and what `factory` does with it when it fails afterwards: `:close` one that `build` created with its destination, and nothing for the wrapper of what the caller still holds (`io:`, `logger:`) or one the caller supplied (`appender:`, `metric:`). Note the two distinct uses of "async": the global `Processor` is one `Async` (the main pipeline thread), and an *individual* appender can additionally be made async/batched.

The thread + queue machinery itself lives in **`SemanticLogger::QueueProcessor`** ([lib/semantic_logger/queue_processor.rb](lib/semantic_logger/queue_processor.rb)), an internal class that the proxy delegates to. It owns the worker thread, lag checking, non-blocking drop mode, the processed count, and **both** processing loops (streaming vs. batched, switched by `batch?`), with collaborators under [lib/semantic_logger/queue_processor/](lib/semantic_logger/queue_processor/): `Inbox` (the capped or uncapped queue, which process created it, and adding to it with or without waiting for room), `Backoff` (failures in a row, `async_max_retries`, the back-off waits, the count of flush/close requests waiting on the worker, which each `Request` counts itself out of exactly once, and only a fork clears, whether the process is exiting, and the failure after which the worker discards the queue ahead of the next request), `HeldWrite` (the entry or batch held to be written again, and how many times it has been after the destination answered with a failure, at most `MAX_RESENDS`, 3), `Reporter` (reports to the internal logger, and the dropped/failed counters), `Reopener` (reopens the wrapped appender on the worker thread, between writes, once `#reopen` asked), `BatchFailure` (what became of a batch whose write raised a message error: the entries stored, those to discard, and the parts to write again, using `#rejected_entry` or splitting in halves), `ThrottledCounter` (counts a problem, such as a dropped message, for a report at most once per interval, trap-safe), and `Request` (a flush or close and its reply). `Async` is a thin proxy: it forwards `name`/`level`/`logger`/… to the wrapped appender and `log`/`flush`/`close`/`reopen`/`queue`/`batch?`/`batch_size`/… to its `QueueProcessor`.

When an appender raises, `QueueProcessor` asks the appender's `#message_error?` whether the log message's content caused it (discard and count it, no back-off; a failed batch is first split in halves to isolate the messages at fault when `#batch_all_or_nothing?` is true, unless `#fails_any_batch?(exception)` says the error would fail any batch, such as a request refused for its credentials; `#message_error?` also covers such errors, which writing again cannot fix) or the destination did. For a destination error it backs off (1s, 2s, ... until `async_max_retries`, then the worker stops for good), then writes the same entry or batch again only when the appender's `#wrote_nothing?(exception)` says the failed write wrote none of it and is worth trying again, at most `HeldWrite::MAX_RESENDS` (3) times after the destination answered with a failure before it discards and counts it and carries on; a write the appender's `#not_sent?(exception)` says never reached the destination is not counted, so an outage loses nothing until `async_max_retries` (the `Appender::Http` family says wrote-nothing for a 408, 429, or 503 response or a connection never made, and the OTLP appenders, through `Otlp::Exporter`, for a 502 or 504 too, as OTLP/HTTP asks, and not-sent for the latter, from the error's class alone, never its `cause`, which Ruby sets to whatever error was being handled); otherwise it discards and counts it before backing off, since resending could duplicate entries. While a flush or close is waiting, a failed write is discarded and counted instead, without a back-off, submitting one ends the back-off under way, and once a write fails while it waits, the entries queued ahead of it are discarded and counted without being written (`Backoff#give_up?` / `#gave_up`), until a request has run, so that a flush does not wait for each entry to fail in turn (a batching worker discards only those it takes off the queue ahead of the first request in its pass, and writes the rest). At exit, `at_exit` in [lib/semantic_logger.rb](lib/semantic_logger.rb) first sets `SemanticLogger.appenders.process_exiting = true` (→ `Appenders#process_exiting=`, which reports an appender that raises and still tells the others → each `Async#process_exiting=` → `QueueProcessor#process_exiting=` → `Backoff#exiting=`, trap-safe; not plain `exiting=`, which a custom appender could define for its own purpose), which counts as a request waiting until the flush has returned, since the main worker can be blocked pushing into the full queue of an appender that is backing off and so would reach it with the flush only much later; it is set back to false afterwards, since test frameworks run their tests in a later at_exit hook. `Appenders` also records it: while the process exits, an appender without a queue of its own (no `process_exiting=`) whose write fails other than for a `#message_error?` is skipped by `Appenders#log` (the messages counted) until it no longer exits, since the main worker writes to it inline and never backs off, so the flush at exit would otherwise wait for each queued message to fail in turn. `#flush` reports the count, then still flushes it, so that it delivers what it already accepted (such as the messages a `:kafka` producer holds). The flag holds the exiting process's pid, so a child forked meanwhile is not exiting. Built-in appenders format through `Subscriber#format_log` / `#format_batch`, never `formatter.call`, so that any formatter error arrives as a `Subscriber::FormatError`; appenders whose client raises its own content errors (UDP, MongoDB, Graylog) override `#message_error?`, and `:new_relic_logs` answers true for every error, since its agent only buffers the entry in-process (a nil agent before newrelic_rpm is initialized is not an outage worth backing off for). Text rendering of untrusted structures goes through `Utils.safe_inspect`, which checks depth before calling `#inspect`: on macOS a second C-level stack overflow on the same thread crashes Ruby, so rescuing `SystemStackError` is only a last resort.

There used to be a separate `Appender::AsyncBatch < Async` subclass; it was removed in v5 once batching moved entirely into `QueueProcessor`. `batch: true` now returns a `SemanticLogger::Appender::Async` (with `batch?` true), not an `AsyncBatch`. If you reintroduce a batch-specific proxy, keep the single `QueueProcessor` as the engine rather than duplicating the loops.

**Backward-compat bar for appenders/formatters:** anyone may have written their own `Subscriber`-derived appender or a custom formatter, so treat the appender/formatter contract as public even though the classes are nominally internal. Concretely: an appender's `#log(log)` / `#batch(logs)` / `#flush` / `#close` / `#reopen` / `#should_log?(log)` signatures, the `#batch` + `#batch_by_default?` opt-in mechanism (and the optional `#batch_refusal`, nil or why the appender cannot be batched, with the private `#format_batch_refusal` helper that it can return, as docs/config.md shows), the optional hooks that decide what happens to a write that raised (`#message_error?(exception)`, `#batch_all_or_nothing?`, `#fails_any_batch?(exception)`, `#wrote_nothing?(exception)`, `#not_sent?(exception)`, `#rejected_entry(exception)`, each optional, with a default in `Subscriber`), the optional `#source_captures` (see below), and a formatter's `#call(log, logger)` signature must keep working unchanged. The `Log` object handed to appenders is **not frozen**: appenders/formatters may continue to read and (historically) mutate it on the worker thread; do not introduce `Log#freeze` on the queue hand-off without a major-version change.

### Factory pattern

`SemanticLogger.add_appender(**args)` is the single public entry point for adding destinations. It delegates to `Appender.factory` → `Appender.build`, which dispatches on the keyword used: `file_name:`, `io:`, `logger:` (wraps an existing Ruby/Rails logger), `appender:` (a Symbol naming a built-in appender, or a `Subscriber` instance), or `metric:`. Formatters are resolved the same way via `Formatters.factory` ([lib/semantic_logger/formatters.rb](lib/semantic_logger/formatters.rb)) — a Symbol like `:json`/`:color`/`:logfmt`, an object responding to `#call`, or a Proc.

To add a new appender or formatter, add the class under the respective directory and register it in the `autoload` list in [lib/semantic_logger/appender.rb](lib/semantic_logger/appender.rb) or [lib/semantic_logger/formatters.rb](lib/semantic_logger/formatters.rb). Appenders for third-party services keep their backing gem **optional** — it is required lazily inside the appender, and listed in the `Gemfile` (for tests) and `README.md`, but never added to the `gemspec`.

### Cross-cutting concepts

- **`Log`** ([lib/semantic_logger/log.rb](lib/semantic_logger/log.rb)) — the immutable-ish value object passed through the whole pipeline. `assign` populates it and can return `false` to suppress logging (e.g. `min_duration` not met). `NON_PAYLOAD_KEYS` controls which keyword args are first-class fields vs. folded into `payload`.
- **Levels** ([lib/semantic_logger/levels.rb](lib/semantic_logger/levels.rb)) — `:trace, :debug, :info, :warn, :error, :fatal`. Comparisons use a pre-computed integer `level_index` for speed; this is a recurring performance pattern, do not replace it with symbol comparisons.
- **Tags & named tags** — thread-local context stored in `Thread.current[:semantic_logger_tags]` / `[:semantic_logger_named_tags]`. The fast paths (`SemanticLogger.tagged`, `.push_tags`, `.fast_tag`) assume clean string tags; the slower instance methods on `Base` flatten/reject-empty for Rails compatibility.
- **`on_log` subscribers** ([lib/semantic_logger/logger.rb](lib/semantic_logger/logger.rb)): the application's callbacks, run **inline on the calling thread** (before the queue hand-off) so they can capture request-scoped context. Keep them fast. Appenders do not use them.
- **Source captures** ([lib/semantic_logger/source_captures.rb](lib/semantic_logger/source_captures.rb)): an appender (or its formatter, which `Subscriber#source_captures` returns by default) answers `#source_captures`, callables that keep on the entry what only the logging thread knows, with `Log#capture` or `Log#capture_backtrace!`. `Appenders` builds the plan (`SourceCaptures`, from its members, each capture once with the appenders using it, an appender whose `#source_captures` raises reported once and given none) in its `SourceCaptures::Current`, held apart from the list because JRuby synchronizes every method of a `Concurrent::Array`, rebuilt by every Array method that changes the list and when `SourceCaptures.changed` was counted (`Subscriber#formatter=`); `Processor#log` / `SyncProcessor#log` run it on the logging thread via `Appenders#current_captures`, after the `on_log` subscribers, skipping a capture unless an owner's `#writes_level?(log)`. So a capture follows membership in the appenders, never construction or close, and the internal logger, never in `Appenders`, runs none. `#log_captured` takes an entry already captured (from another Ractor, whose `RactorProcessor#log` runs the published shareable captures, `SourceCaptures.shareable`). No backtrace is captured for every entry by default: `backtrace_level` is deprecated and nil, `call_site_level` defaults to `:error`, and the error-service appenders (`:sentry_ruby`, `:bugsnag`, `:honeybadger`) and `Test::CaptureLogEvents` capture their own.
- **Forking**: after `fork`, file handles and the queue must be re-created via `SemanticLogger.reopen` → `Processor#reopen` (an `Async`) → its worker thread runs `Appenders#reopen` → each `Async#reopen` → `QueueProcessor#reopen`, which asks its own worker thread to reopen the wrapped appender (`QueueProcessor::Reopener`) before it writes again. After a fork, `Processor#reopen` first replaces each `Async`'s queue and worker on the calling thread (`Appenders#renew_after_fork` → `QueueProcessor#renew_after_fork`), so that they run when `reopen` returns. Reopening an appender is never done on the calling thread, which is often a signal trap and may race a write; only `SyncProcessor` reopens inline, and then only the appenders without a thread of their own. The worker thread reopens before it next takes entries off its queue, so a batching one reopens at its next batch or flush; `#reopen` queues a `:reopen` marker only for a streaming worker, to wake it, and the marker is neither a `Request` nor counted as waiting. `QueueProcessor#reopen` asks for the reopen before it replaces the queue and worker after a fork, so the child's worker reopens before it writes anything. As of v5 this happens automatically: a `Process._fork`/`daemon` hook ([lib/semantic_logger/core_ext/process.rb](lib/semantic_logger/core_ext/process.rb), prepended in [lib/semantic_logger.rb](lib/semantic_logger.rb)) calls `reopen` in the child unless `SemanticLogger.reopen_on_fork = false`. `reopen` is guarded to run once per process (pid-based; bypass with `reopen(force: true)`). `at_exit` in [lib/semantic_logger.rb](lib/semantic_logger.rb) flushes the queue on shutdown, telling each async appender that the process is exiting for the duration of that flush (see above).
- **OTLP** ([lib/semantic_logger/otlp/](lib/semantic_logger/otlp/)): `appender: :otlp` (`Appender::Otlp`) and `metric: :otlp` (`Metric::Otlp`) send OTLP/HTTP without OpenTelemetry gems or `google-protobuf`. `formatter: :otlp_json_lines` (`Formatters::OtlpJsonLines`) writes the same log records to a file, one `LogsData` per line, for the Collector's `otlpjsonfile` receiver, composing a `Formatters::Otlp` rather than subclassing it (`Appender::Otlp` accepts any `Formatters::Otlp`). What they share lives in the internal `SemanticLogger::Otlp`: `Exporter` (a mixin for an `Appender::Http` subclass that answers `#otlp_signal`: options, environment defaults, partial success), `Resource` (the resource attributes: which of the given values, `OTEL_*` variables, and defaults wins, and `process.pid`), `LogsData` (the ResourceLogs/ScopeLogs envelope of log records), `Environment` (the `OTEL_*` variables of a `Signal`), `Protocol` (http/protobuf or http/json), `Protobuf` (a hand-written wire encoder and decoder) driven by `Schema` (the field numbers of opentelemetry-proto), `Values` (AnyValue, text, times), and `TraceContext` (the span or `trace_id`/`span_id` named tags of a log record). Each encoder builds its request once, as the Hash of the JSON encoding, and `Protocol` writes it in either encoding. A new field must be added to `Schema`, with its number checked against the `.proto` files.
- **`Loggable`** ([lib/semantic_logger/loggable.rb](lib/semantic_logger/loggable.rb)): mixin giving a class both `self.logger` and instance `logger`. A module that includes it gives its own instance methods a `logger` in any class that includes the module. To time code, use the `measure_*` methods of the logger; for method-level tracing, defer to OpenTelemetry (`tracer.in_span`) or an APM agent rather than adding a method-wrapping helper here (`logger_measure_method` was an experiment, removed in v5.3).

## Testing conventions

- The standard way to assert on emitted logs is the in-memory appenders ([test/in_memory_appender.rb](test/in_memory_appender.rb) and helpers) — add a capturing appender and inspect the `Log` objects, rather than parsing formatted output.
- For testing application code that uses Semantic Logger, the gem ships `SemanticLogger::Test::CaptureLogEvents` and `SemanticLogger::Test::Minitest` ([lib/semantic_logger/test/](lib/semantic_logger/test/)).
- Appender tests for external services use mocks/fakes (e.g. [test/mocks/](test/mocks/), `test/appender/fake_bunny.rb`) rather than real connections, except MongoDB.
- Report a deprecation with `SemanticLogger::Deprecation.warn(message)` ([lib/semantic_logger/deprecation.rb](lib/semantic_logger/deprecation.rb), copied from IOStreams), never `Kernel.warn` directly: it names the application's line and only reports while `Warning[:deprecated]` is on. A test that reports one fails unless it asserts it with `assert_deprecated(/pattern/) { ... }`, or its describe block allows it with `allow_deprecation(/pattern/)` ([test/deprecation_check.rb](test/deprecation_check.rb)), so the gem never uses its own deprecated features unawares.

## Known tech debt

Standing items, tracked here so sessions know what is intentional versus worth fixing. Removals or contract changes wait for a major version.

- **rails_semantic_logger v6: no `formatter: :color` with `appender:` or `metric:`.** Its `Appenders#defaults` merges `formatter: :color` into every `add_server` and `add_console` declaration, which v6 refuses with an appender instance (`Appender.subscriber_instance`) and with any metric appender (`Metric::Snapshots`). Its v6 release must add it only with the default stream or `io:` / `file_name:`, and a 5.x release of it should require `semantic_logger < 6` before 6.0.0 ships. Until then, `formatter: nil` avoids the raise (see the v6 upgrade notes).
- **v6 security follow-ups.** Deferred from the v5.2 security fixes because they change public behaviour: accept log arguments (`duration`, `min_duration`, `metric`, `log_exception`, ...) only as real keyword arguments, so that a payload hash is never interpreted (v5.2 only validates the values); and consider enabling `escape_control_chars` by default in the text formatters.
- **`appender: :open_telemetry`: remove in v7.** As of v6 [open_telemetry.rb](lib/semantic_logger/appender/open_telemetry.rb), which writes through the `opentelemetry-logs-sdk` gem, warns that it is deprecated, superseded by [otlp.rb](lib/semantic_logger/appender/otlp.rb) (`appender: :otlp`, OTLP/HTTP with no OpenTelemetry gems), and the docs describe only `:otlp`. Remove it, and `Formatters::OpenTelemetry` once `Formatters::Otlp` no longer builds on it, in v7.
- **rubocop_todo backlog.** `.rubocop_todo.yml` suppresses 26 cop categories (down from 32; `Layout/LineLength` was restored to the standard `Max: 120` and four cops were cleared in the 5.1 cycle). Treat it as a burn-down list: when touching a file, prefer fixing its suppressed offenses over adding new ones; never add to the todo file. Most of the remainder is complexity metrics (`Metrics/*`) and test-only cops (`Minitest/*`) that need refactoring rather than mechanical fixes.
